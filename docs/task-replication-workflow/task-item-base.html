BP_Task_Item_Base

In-World Actor  — interaction detection & RPC bridging

Role in New Architecture
BP_Task_Item_Base is responsible for detecting the interaction and bridging to the server. It does not own any authoritative task state. All persistent progress lives in BP_GS_Gameplay.

Full Interaction Flow

Step-by-Step Walkthrough

1

Event Interact fires on the client. The player presses the interact key. The interaction event fires on the client that owns the interacting pawn.

2

FlipFlop / Branch validates the interaction. The existing FlipFlop or condition node determines whether this is a valid new interaction (e.g., not already interacted, cooldown passed). Optional client-side feedback (sound, particle, animation) can fire here.

3

Server RPC called on PlayerState. The client calls Server_ReportTaskCompleted(TaskID) on its own BP_PS_Gameplay. This is a Run on Server / Reliable RPC. Because PlayerState is owned by the client, this RPC is always valid.

4

Server receives RPC and calls GameMode. On the server, Server_ReportTaskCompleted runs inside BP_PS_Gameplay. It immediately calls GetGameMode → Cast BP_GM_Gameplay → OnTaskCompleted(TaskID).

5

GameMode deduplicates and writes to GameState. BP_GM_Gameplay.OnTaskCompleted checks GloballyCompletedTaskIDs.Contains(TaskID). If the task is already done, it returns early. Otherwise it writes the TaskID to GameState and increments the counter.

6

GameState replicates to all clients. Because GloballyCompletedTaskIDs is RepNotify, Unreal automatically sends the updated array to every connected client and fires OnRep_CompletedTaskIDs.

7

UI refreshes everywhere. OnRep_CompletedTaskIDs calls into the HUD / open widgets. Every player's tablet now shows the task as complete — without reopening it.

⚠ Avoid GetPlayerController(0)

Multiplayer Bug — Do Not Use
The current task item graph contains a node chain: Get Player Controller (0) → Get Player State → Cast BP_PS_Gameplay.

In a multiplayer game with dedicated server, Player Controller index 0 on the server is not the interacting player — it is whichever client happened to be first. This will cause task progress to be attributed to the wrong player.

Instead, use the Player That Interacts reference passed by the interaction event, and call GetPlayerState on that pawn's controller. 
// WRONG — do not use in multiplayer
Get Player Controller (0)
  → Get Player State
  → Cast to BP_PS_Gameplay
  → Call Server_ReportTaskCompleted(TaskID)

// CORRECT
Player That Interacts (from Event Interact)
  → Get Controller
  → Get Player State
  → Cast to BP_PS_Gameplay
  → Call Server_ReportTaskCompleted(TaskID)

Variables to Keep in BP_Task_Item_Base

VariableTypePurpose
TaskID Name Unique identifier for this task. Must match the key used in GameState maps.
bInteracted Boolean Local guard to prevent re-triggering interaction events. Does not need replication.
InteractCooldown Float Optional cooldown between interactions (e.g., for multi-step tasks).
RequiredInteractions Integer Goal value fed into GameState.TaskGoalMap on server BeginPlay.
Good Practice
During server BeginPlay (or OnRegisterTask), each BP_Task_Item_Base should register itself with the server GameState — passing its TaskID and RequiredInteractions to populate TaskGoalMap. GameMode can handle this registration in its BeginPlay via Get All Actors Of Class → For Each → GameState.RegisterTask(Actor).
